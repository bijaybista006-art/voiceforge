# VoiceForge — Claude context

## What this is
Voice cloning + long-form narration studio. Next.js on Vercel (free), TTS models on
free Colab T4 GPU exposed via Cloudflare tunnel. Zero cost, zero API keys.

## Hard constraints
- Vercel has NO GPU. Never put model inference in a Next.js route.
- Backend URLs live in server-side storage — see "Rules that CHANGED" below.
- Generation is SEQUENTIAL. One GPU. Never parallelize /generate calls.
- Every completed chunk writes to IndexedDB immediately. Disconnects must lose nothing.
- MAX_CHARS = 240 per chunk. This is load-bearing — longer chunks make both models drift.
- Qwen3 cloning requires ref_text (the sample transcript). Do not make it optional.
- `signal` orange (#FF6B4A) is ONLY for live/recording/generating. Never a button colour.
- Backend runs Chatterbox Multilingual (23 langs incl. en/hi — NO Nepali).
- Expressive Nepali (opt-in per request: code_switch / prosody_tags / speed):
  decisions in backend/voiceforge_lang.py (tested, no torch), model driving in
  _render_expressive in voiceforge_server.py. English runs use the stock model
  with language "en" and the voice's linked `refs.en` voice; tone tags pick
  TONES presets and `refs.<tone>` voices. Any failure falls back to the plain
  path. Tags are kept through normalize only when prosody_tags is set.
  GenParams.language is the language_id. Number/abbreviation expansion in
  normalize.ts is English-only; the chunker treats । and ॥ as sentence ends.

## Storage — Supabase only (moved Oct 2026)
- Vercel hosts the frontend and nothing else. No app code uses Vercel Blob
  or Upstash any more; do not add a Vercel storage product back. The move was forced: Blob
  bills every put/copy/list as an "advanced operation" (2,000/month free) and
  a batch job is one put per item, which paused the whole team.
- `lib/storage.ts` is the ONLY file that talks to Supabase. Service-role key,
  server side only. The browser never talks to Supabase; the anon key is
  unused and RLS is on with no policies.
- Files: one PUBLIC bucket `voiceforge-audio`, same paths as before
  (voices/, jobs/, presenter-clips/, presenters/, assets/, uploads/). Public
  because backends, n8n and renders fetch by plain URL and a job's audio_url
  must not expire. Every stored file has a row in `audio_files`; lists come
  from that table (`listAudio`), never from listing the bucket.
- Data: one `kv` table (key, jsonb value, expires_at) holding the same key
  names as before (`vf:voice:<id>`, `vf:job:<id>`, …). `lib/server/redis.ts`
  and `lib/server/blob.ts` are thin shims over lib/storage.ts that keep the
  old function names, so voice/job/backend code did not change. Counters,
  locks and rate limits are SQL functions (`kv_incr`, `kv_set_nx`,
  `rate_limit`) because they must be atomic — do not rebuild them as
  read-then-write in TypeScript.
- Schema: `supabase/migrations/0001_voiceforge_storage.sql`. Prove a project
  is set up right with `node --env-file=.env.local scripts/check-supabase.ts`.
- Direct uploads (admin Presenters page) use signed upload URLs. A signed
  URL pins the PATH only — not type or size. The presenter route accepts only
  files in our bucket under presenters/<kind>/, and the bucket caps files at
  50 MB and to audio/video/png/jpeg/webp.
- Free plan limits that matter: 1 GB of files, 50 MB per file, and the
  project PAUSES after 7 days with no activity. The daily cleanup cron is
  what keeps it awake and what keeps it under 1 GB.
- GPU backends never touch Supabase. They download by public URL and hand
  audio back to the gateway. No Supabase key belongs in Modal or a notebook.

## Video rendering is NOT VoiceForge's job (removed Oct 2026)
- VoiceForge does voice (TTS, cloning, library, /api/v1), presenter clips
  and AI-generated clips (Wan, see below). Every other video — assembling
  scenes, captions, music into a finished video — is rendered by the user's
  n8n workflows on their own render server (HyperFrames). Do not add a
  renderer back. Generating a clip from a prompt is not rendering.
- Removed: backend/voiceforge_render.py, lib/server/videojobs.ts,
  /api/v1/video, /api/v1/uploads (create/complete), lib/server/assets.ts and
  the Assets admin page.
- Kept on purpose: the `render` function in modal/voiceforge_modal.py and the
  notebook line that downloads voiceforge_render.py. Both share a deploy with
  voice and presenter; they now find nothing and do nothing. The voice server
  mounts render routes only if the module imports, so it carries on without.
- Scene uploads are gone entirely: lib/server/uploads.ts was removed and the
  466 leftover files (368 MB) under uploads/ were deleted on 2026-10-17.
- Old job records with kind "video" are left as they are by every route until
  the retention sweep removes them.

## Training data (Admin → Model training → Training data, Oct 2026)
- Collects clips + exact transcripts per language (ne, en) and per speaker
  for a future fine-tune. Part 1 only: nothing trains yet and nothing here
  changes TTS. Kept apart from Voices on purpose (own sidebar section).
- Each clip: audio, transcript (word for word, the training text), optional
  description (notes, never in the .txt dataset), speaker (required; matched
  without case; clips from before speakers existed list as "Unnamed").
- Manifest takes ?speaker= — one speaker per training run.
- lib/trainingChecks.ts (pure, tested): trimming, length 3–20 s, clipping,
  level, long pauses, transcript-length plausibility. The browser runs them
  and resamples to 24 kHz with OfflineAudioContext (not linear) before upload.
- lib/server/training.ts: records at vf:sample:<id>, files at
  training/<lang>/<id>.wav. NO index list — listed by key prefix (kvScan),
  because read-then-write indexes lose entries. Never swept.
- Server refuses anything but 24 kHz mono 16-bit WAV, so every stored clip
  passed the browser checks.
- Transcripts are stored as typed (natural spelling). When a training run is
  built, decide whether to apply the same text preparation as inference
  (prepareNepali respellings, normalize) — train and inference must match.
- Built-in sentences: lib/trainingPrompts.ts. Ids are stable; append only.

## Presenter video (replaced the talking-head feature, Oct 2026)
- The old SadTalker/Wav2Lip system is GONE: colab/voiceforge_video.ipynb,
  lib/videoStore.ts, lib/videoBackend.ts, components/VideoLab.tsx and the
  pasted tunnel URL were all deleted. Do not reintroduce a second, hand-pasted
  backend — video uses the registry like everything else.
- lib/server/presenters.ts is the library and the routing rule. A presenter is
  a "recording" (re-lipped; capability "presenter-relip") or an "image"
  (animated; capability "presenter-animate"). Each kind is routed in the
  standard order among backends that report its capability.
- Per-backend `videoEnabled` (absent = on) is a presenter-only switch. The
  voice path never reads it.
- Recordings WORK on Modal: backend/voiceforge_presenter.py runs LatentSync
  1.6 (pinned commit) in its own Modal function `presenter` on an L4. It is
  called as a subprocess from the LatentSync checkout. Measured 2026-10-11:
  7.7s of audio took 269s of engine time (~35x real time), ~$0.06.
  1.6 needs ~18 GB so it cannot run on a T4; 1.5 (8 GB, 256 px) could.
- Quality defaults (Oct 2026, presenter v1.4.0, after the user judged lip
  sync poor): steps 40 (was 20), guidance 2.0 (was 1.5), DeepCache OFF (was
  always on; VOICEFORGE_PRESENTER_DEEPCACHE=1 re-enables). ~3x slower, so
  ENGINE_TIMEOUT 100 min (was 40) and PRESENTER_STALE_AFTER_MS 120 min (was
  45). The 269s measurement above is from the old defaults; not re-measured.
  Next step if still poor: InfiniteTalk (Wan 2.1 14B, audio-driven
  video-to-video) as a second engine on a large Modal GPU — test first.
- Image presenters have no engine yet (candidates: Wan2.2-S2V, InfiniteTalk).
- POST /api/v1/presenter -> job kind "presenter" -> clip copied to storage under
  presenter-clips/. Modal's presenter address is discovered automatically and
  stored as presenterUrl / presenterCapabilities, separate from capabilities.
- IndexedDB still declares the v2 `videoAssets` store so existing browsers
  open their database without an upgrade; nothing reads or writes it.

## AI video clips — Wan 2.2 TI2V-5B (added Oct 2026)
- Text → 24 fps MP4 clip, `Wan-AI/Wan2.2-TI2V-5B-Diffusers` (Apache 2.0).
  Capability `text-to-video`. Phases A (backend), B (gateway, API, job kind
  "clip") and C (studio) DONE.
- Studio: ViewId "clips", sidebar "AI Video" under Presenter Video, icon
  IconFilmSpark. Shares the video (violet) accent with Presenter Video —
  `isVideoView()` in Shell.tsx. components/views/ClipView.tsx is modelled on
  VideoView.tsx; lib/clipClient.ts is the only browser code for clips and
  talks to /api/gateway/clips only. Last clip id + start time in
  localStorage `vf:ai-clip` (per-browser convenience, safe to lose).
  "Reuse settings" loads a finished clip's settings (seed included) back
  into the form. Home has a third card (ClipCard). Progress bar uses the
  `live` tone only while generating.
- Grids holding a <pre> need `grid-cols-1` + `min-w-0` columns: an implicit
  `auto` track grows to the pre's longest line and pushes the page sideways
  on a phone.
- Gateway: `lib/server/clipjobs.ts` — a copy of the presenter flow, not a
  generalisation of it (presenterjobs.ts is untouched). Backend row fields
  wanUrl / wanCapabilities / wanProbedAt / wanProbedUrl / wanNote / wanLimits,
  kept apart from `capabilities` like the presenter fields and forgotten when
  a notebook's url changes. Probed at the CPU health address (Modal) so a
  probe never wakes the L40S. `videoEnabled: false` blocks clips too.
- Job kind "clip": `job.clip = {request, appUrl, settings?, restarts?,
  failedOn?}`. A failed clip moves to the next backend (a T4 OOM → Modal)
  keeping the first backend's seed; a lost one is resent once; stale after
  100 min. MP4 copied to `clips/<id>.mp4` (FileKind "clip"); >48 MB stays on
  the backend (bucket caps 50 MB). deleteJob already removes videoUrl, so the
  retention sweep needed no change.
- Quota counts characters to speak; a clip speaks none, so `/api/v1/clips`
  only calls checkQuota(key, 0) — an over-limit key is still refused.
- Own folder `backend/wan/` (settings / engine / install / service — see its
  README). Only engine.py imports torch. settings.py is the single place for
  limits, defaults, profiles and pins; tested in backend/tests/test_wan.py.
- Same job protocol as the presenter (`/render`, `/render/{id}`, `/video`,
  DELETE, `/health`), so collection follows the 4.5 MB rule unchanged.
  Callback body has `kind: "clip"` and the full resolved `settings`.
- Modal: its OWN app `modal/voiceforge_wan.py` ("voiceforge-wan"), deployed
  after voice by deploy-modal.yml, so a Wan build failure never blocks voice.
  L40S, profile `full` (bf16, 720p default), weights in volume `wan-models`
  (download function, run by the workflow; HF_HUB_OFFLINE=1 in the image so
  a run never downloads). URLs (live): `bijaybista006--voiceforge-wan.us-east.modal.run`
  (GPU) and `…--voiceforge-wan-health.us-east.modal.run` (CPU /health — poll
  THIS one, an idle L40S is ~$2/h). NOTE the region: Modal gives apps created
  after it added regions `<label>.<region>.modal.run`, while the older voice
  app keeps `…-api.modal.run`. So wanCandidateUrls returns several forms (the
  voice URL's own first, then regional) and discoverWan keeps the first that
  answers in wanProbedUrl/wanUrl. Don't "simplify" it back to one derived URL.
- Notebooks: OFF unless `ENABLE_AI_VIDEO = True` in Cell 0 (sets
  VOICEFORGE_WAN=1; it downloads ~25 GB). Mounted under `/wan`; private
  Python 3.11 venv in /tmp/voiceforge-wan built in the background (Wan's
  diffusers/transformers clash with Chatterbox's pins), engine run as a
  subprocess per clip. Profile `low_vram`: 4-bit NF4 + fp16 (T4 has no bf16),
  tiled VAE, 480p default. Single GPU → takes the voice `_GPU_LOCK` for the
  whole clip (narration waits). Kaggle T4 x2 → clip runs on GPU 1, no lock.
- One pinned stack everywhere: torch 2.7.1 (PyPI wheel = CUDA 12.6, works on
  Modal/Colab/Kaggle drivers). The Modal file repeats WAN_PACKAGES; a test
  keeps it identical to settings.py.
- Not run on a GPU yet by the code author — first real runs are the user's.

### Public API (Phase 5)
- Auth is `Authorization: Bearer vf_live_…`. Keys are 256-bit, shown ONCE, and
  only a SHA-256 hash is stored — lookup is by hash, so verification is one
  key read, and there is deliberately no key recovery, only reissue.
- Order inside every `/api/v1` handler: authenticate -> parse body ->
  `checkQuota`. Auth comes first so an unauthenticated caller can't probe the
  schema or make the server do work. Don't reorder this.
- Everything except `/api/v1/audio/speech` is asynchronous. A Vercel function
  is capped at 60 s and a Modal cold start eats most of it, so no request may
  wait for a render. `/audio/speech` is synchronous and therefore capped at
  600 characters.

### Job contract — the 4.5 MB rule
- Audio NEVER travels in a request body. Vercel rejects bodies over 4.5 MB and
  a 15-minute narration is far bigger. The backend writes renders to disk,
  POSTs metadata only to `/api/internal/jobs/{id}/complete`, and the gateway
  pulls each file with `GET /jobs/{id}/audio/{n}` — a response has no cap —
  then DELETEs the backend's copy. Don't "simplify" this by putting audio_b64
  back in the callback.
- Completion must never DEPEND on the callback. `reconcileJob` re-checks the
  backend whenever a running job is polled (public API and admin Jobs page),
  so a tunnel dying between "render finished" and "POST sent" costs a poll,
  not the render. A 404 from the backend means a restarted Colab -> error.
- The callback token is HMAC-ish: SHA-256 of `jobId:BACKEND_SECRET`. Derived,
  not stored, and valid for exactly one job.

### Rules that CHANGED (supersede older entries below)
- Backend URLs live in server-side storage (registered by backends or set in
  admin). Still never hardcoded, still never env vars.
- The app is not open: everything is behind admin login except machine
  endpoints (`/api/v1` API key, `/api/backends/register` token,
  `/api/internal` callback token).
- **The browser never calls a GPU.** `lib/server/gateway.ts` is the only place
  that knows a backend URL or `BACKEND_SECRET`; the studio posts to
  `/api/gateway/generate`. `/api/proxy` and the client-side GPU functions in
  `lib/backend.ts` were deleted in Phase 4 — do not reintroduce either, or the
  secret leaks and an unauthenticated relay comes back. `lib/backend.ts` now
  holds only `BackendError` and `normalizeBackendUrl` (the video backend, which
  is deliberately outside the registry, still calls its own URL directly).
- **No cloning step.** Voices are a server-side library referenced by id. The
  gateway PUTs the clip on a 409 `voice_not_cached` and retries once — that one
  rule is why a Colab restart, a backend switch or a different browser never
  needs a re-clone. Don't add a browser-side clone path back.

### Voice library (Phase 4)
- `lib/server/voices.ts` — metadata in the kv table (`vf:voice:<id>`, index
  `vf:voices`, default `vf:voice:default`), clip in the bucket at `voices/<id>.wav`.
- Clips are ALWAYS 16-bit PCM WAV. The browser decodes and re-encodes before
  upload because the GPU hosts read clips with soundfile, whose MP3 support
  depends on the libsndfile build. Don't accept MP3 server-side.
- `resolveVoice(id?)`: explicit id → default → the only voice if there's
  exactly one. First voice added becomes the default automatically.
- Deleting the default promotes another rather than leaving a dangling id.

### Auth (Phase 1)
- One admin user. `ADMIN_PASSWORD` + `SESSION_SECRET` env vars, no Supabase
  Auth, no external auth. `lib/server/auth.ts` is dependency-free Web Crypto so it
  runs in Edge middleware; session = HMAC-signed cookie, 12 h, no store
  (rotate SESSION_SECRET to sign everyone out).
- LOAD-BEARING SAFETY: `middleware.ts` only gates when BOTH vars are set. An
  unconfigured deploy stays open on purpose so shipping can never lock the
  owner out of their live site. Do not "fix" this by gating unconditionally.
- Storage degrades gracefully the same way: no Supabase env ⇒ features
  report "not connected", never crash. Storage is a feature, not a boot
  requirement — `lib/store.ts` hydrate() must always finish.

## Backend contract v2 (every call carries X-Backend-Secret except /health)
GET  /health           → { ok, provider, gpu, models[], voices_cached[], busy, version }
PUT  /voices/{id}      → { audio_url, transcript, language } → caches the clip
POST /generate         → { text, voice_id, model, seed, ...params }
                         → { audio_b64, sample_rate, duration, gen_seconds }
                         → 409 { error: "voice_not_cached" } if the id is unknown
POST /jobs             → 202; long renders + part uploads (Phase 5 uses this)
POST /clone            → kept for backwards compatibility only. Not used by the app.

## App API
Studio (admin session):
  GET  /api/gateway/status   → active backend + voice library
  POST /api/gateway/generate → one chunk
Admin (admin session):
  /api/admin/{backends,voices,keys,jobs,settings,session}
Machine endpoints (NOT behind the session — see middleware PUBLIC_PREFIXES):
  /api/v1/*                          → API key
  /api/backends/register             → REGISTRATION_TOKEN
  /api/internal/jobs/{id}/complete   → per-job callback token
  /api/internal/cleanup              → CRON_SECRET or Vercel's cron UA

## Public API v1
GET  /api/v1/voices        → [{id, name, language, duration, default}]
POST /api/v1/tts           → 202 {job_id, status_url}  (stitched narration)
POST /api/v1/tts/batch     → 202, one clip per item, NOT stitched
GET  /api/v1/jobs/{id}     → {status, audio_url?, items?, error?}; reconciles
POST /api/v1/audio/speech  → OpenAI-compatible, returns audio BYTES, ≤600 chars
POST /api/v1/clips         → 202 {job_id, status_url}; AI video from a prompt.
                             Poll /api/v1/jobs/{id} → {video_url, settings}
GET  /api/v1/clips         → {ready, provider?, reason?, limits?}
Studio (admin session): GET/POST /api/gateway/clips, GET /api/gateway/clips/{id}
